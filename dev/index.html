KernelLux.jl

KernelLux lets you evaluate Lux models inside KernelAbstractions kernels that are compiled by Reactant.

Motivation

The standard forward pass Lux.apply(model, x, ps, st) does not compile inside a KernelAbstractions kernel lowered by Reactant. The Dense forward pass relies on machinery (NNlib.fast_act, match_eltype, fused_dense_bias_activation, …) that performs heap allocation and string/Symbol handling for which there is no device lowering; the compiler raises an InvalidIRError with reasons such as calls to utf8proc_toupper, jl_alloc_genericmemory_unchecked, and jl_argument_error.

KernelLux provides a drop-in replacement, apply_in_kernel, that has the same signature and return value as Lux.apply but is written entirely with scalar and StaticArrays operations that lower cleanly to the device.

Scope

Small to medium networks only

KernelLux targets small to medium sized networks — the narrow multilayer perceptrons that appear in hybrid / physics-informed models, evaluated pointwise inside a larger simulation kernel. Large networks (wide hidden layers) are slow in this per-thread setting: each thread holds the entire hidden activation vector, so GPU occupancy collapses. See Performance for numbers. If you can express your workload as a single batched matrix multiply, prefer the ordinary model(xmat, ps, st) forward pass.

Supported layers: a Lux.Chain of Lux.Dense layers, with or without bias, and with any device-safe scalar activation function (tanh, relu, identity, …).

Quick start

apply_in_kernel operates on a single sample: x is an SVector of input features and the returned y is an SVector. You build that SVector from your per-thread data inside the kernel.

using KernelLux, Lux, Random, StaticArrays, Reactant, CUDA
using KernelAbstractions: @kernel, @index, get_backend, @Const
import Lux.MLDataDevices as MLDD

dev = MLDD.reactant_device()

model = Chain(Dense(1 => 8, tanh), Dense(8 => 1))
ps, st = Lux.setup(Random.Xoshiro(0), model) |> dev
x   = collect(Float32, -3:0.25:3) |> dev
out = zero(x)

@kernel function eval_kernel!(out, @Const(x), model, ps, st)
    i = @index(Global)
    y, _ = apply_in_kernel(model, SA[x[i]], ps, st)
    @inbounds out[i] = y[1]
end

run!(out, x, model, ps, st) =
    (eval_kernel!(get_backend(out))(out, x, model, ps, st; ndrange = length(out)); nothing)

compiled! = @compile raise = true run!(out, x, model, ps, st)
compiled!(out, x, model, ps, st)

Inside the kernel the parameters arrive as device arrays whose shape is encoded in their type, so apply_in_kernel is fully static and non-allocating without any preparation.

Host (CPU) evaluation

To evaluate the model on the host in a type-stable, allocation-free way (for example in tests), convert the parameters to StaticArrays first with kernelize:

ps, st = Lux.setup(Random.Xoshiro(0), model)
sps    = kernelize(ps)
y, _   = apply_in_kernel(model, SA[0.5f0], sps, st)

Plain Matrix/Vector parameters also work but are type-unstable and allocate on the host.

Reverse-mode gradients

A loss computed by a kernel that calls apply_in_kernel can be differentiated with respect to the network parameters using reverse-mode Enzyme under Reactant. The gradient matches the one obtained from the ordinary batched forward pass.

The one requirement is to compile the gradient with both raise = true and raise_first = true:

using Enzyme

function loss(x, model, ps, st)
    out = similar(x)
    eval_kernel!(get_backend(out))(out, x, model, ps, st; ndrange = length(out))
    return sum(abs2, out)
end

grad(x, model, ps, st) =
    Enzyme.gradient(Enzyme.Reverse, Const(loss), Const(x), Const(model), ps, Const(st))[3]

compiled_grad = @compile raise = true raise_first = true grad(x, model, ps, st)
∂ps = compiled_grad(x, model, ps, st)

raise = true lifts the KernelAbstractions kernel to HLO; raise_first = true runs that raising pass before the optimization/autodiff passes, so Enzyme differentiates the resulting StableHLO operations rather than an opaque enzymexla.kernel_call (which has no adjoint). Without both flags, compilation fails with "could not compute the adjoint for this operation".

See test/gradient.jl for a complete, checked example.

Performance

On an NVIDIA A40, evaluating N = 10⁶ samples, comparing apply_in_kernel in a one-thread-per-sample kernel against the direct batched forward pass model(xmat, ps, st):

modelkerneldirectratio
1 → 4 → 10.06 ms0.06 ms~1.0×
4 → 16 → 16 → 10.94 ms0.56 ms~1.7×
8 → 32 → 32 → 117 ms1.1 ms~16×

The kernel is competitive with the batched matmul for the small, narrow networks it targets. For wide hidden layers it is much slower, because occupancy collapses while the batched path reuses weights across the batch via cuBLAS/XLA. The per-thread kernel is nonetheless the right — and often only — option when the network is evaluated pointwise inside a larger kernel where the matrix multiply cannot be batched out.
